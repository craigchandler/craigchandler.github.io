## Tone and writing style

Public copy should be:

- senior
- technically precise
- restrained
- calm
- professional
- direct
- evidence-based
- editorial rather than promotional

Avoid:

- startup language
- hype
- generic marketing language
- exaggerated claims
- motivational slogans
- "passionate about technology"
- "10x engineer" language
- excessive superlatives
- AI hype
- aggressive calls to action
- résumé-style bullet dumping

Prefer explaining:

- the problem
- why it was difficult
- the engineering judgement involved
- what was actually built
- what evidence supports the outcome

Do not strengthen claims beyond what repository evidence or supplied source material supports.

If uncertain, qualify the wording rather than guessing.

### Editorial execution

Write as a practising engineer explaining work to a technically experienced peer.

- Prefer concrete decisions, constraints, behaviours and results.
- Use first person where it establishes responsibility or explains a decision. Do not begin every paragraph with an ownership statement.
- Establish the overall scope of Craig's contribution once, then identify specific contributions where they matter.
- Let technical facts and outcomes demonstrate capability. Avoid sentences explaining why the preceding facts demonstrate competence.
- Avoid generic closing summaries that merely restate the site's positioning.
- Preserve technical specificity when it helps explain the work.
- Integrate attribution and qualifications where the relevant work is introduced. Avoid repetitive or defensive disclaimers.
- Do not invent difficulty, conflict, novelty or a dramatic transformation. A deliberate design choice or sustained delivery responsibility can be sufficient substance.
- Use Australian English.

Narrative and scannability are complementary. Use meaningful headings, short paragraphs and compact metadata without reducing the case study to fragments or a résumé.

## Case study structure

Case studies should generally answer:

1. What problem existed?
2. Why was it difficult?
3. What was Craig's actual role?
4. What architecture or engineering approach was used?
5. What was built or changed?
6. What evidence demonstrates the outcome?

Do not turn case studies into:

- code documentation
- chronological commit diaries
- framework tutorials
- technology inventories
- sales brochures

Technical detail should support the engineering story.

The questions above are editorial checks, not a mandatory heading sequence. Choose sections that suit the project's actual story.

Preserve the established numbered-section presentation, but do not require the same number or names of sections across all projects.

Place diagrams and screenshots near the text they explain. Architecture does not automatically belong before the problem, contribution or context. Make contribution and technology metadata easy to find near the beginning without duplicating it throughout the page.

Distinguish:

- what the system does;
- what Craig personally contributed;
- why a decision was made; and
- what evidence supports the result.

Do not infer one from another.

## Repository workflow

Before editing:

1. inspect the existing implementation
2. understand the current content model
3. review relevant existing case studies/components
4. avoid unnecessary structural changes

Preserve unrelated uncommitted changes. For non-trivial changes, prefer an appropriate feature branch and reuse an existing task branch where suitable. Do not change branches blindly in a dirty working tree.

Editing and local validation do not authorise committing, pushing, merging or deploying. Perform those actions only when authorised by the user's task. Honour authorisation already supplied in the current task without requesting it again.

Do not modify unrelated case studies as part of a scoped task.

## Validation

Before reporting a task complete, run the relevant checks using the package manager and scripts established by the repository. Inspect the package manifest and lockfile rather than assuming commands exist.

Where these scripts are available and npm is the repository's package manager, run:

```bash
npm run check
npm run build
git diff --check
```

For layout, typography, diagram or image changes, inspect the rendered result at desktop and mobile widths. Check:

- headline wrapping and orphaned punctuation;
- horizontal overflow and narrative reading width;
- section spacing and figure placement;
- diagram label size and contrast;
- screenshot sizing and accurate captions;
- semantic heading order and accessible descriptions;
- relevant links and route consistency;
- affected shared components and unintended changes to other pages.

For approved-copy implementation, confirm that obsolete prose has been replaced rather than appended, and that metadata or related cards do not contradict the revised content.

Do not infer a shared runtime, algorithm, service or binary merely from a conceptual diagram. Keep diagram labels, captions and accessible descriptions consistent with the supported technical relationships.

Avoid adding tests that merely assert approved prose or mirror trivial markup. Use existing checks and proportionate verification. Broaden testing only to resolve a concrete risk or satisfy a repository requirement.

If a check or visual inspection cannot be performed, report the limitation. Do not imply verification succeeded.

Finish with a concise summary of changed files, material content or layout changes, verification performed and any unresolved issues.
